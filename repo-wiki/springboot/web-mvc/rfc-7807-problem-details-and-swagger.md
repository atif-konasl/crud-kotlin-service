## 1. What is RFC 7807 (`ProblemDetail`)?

[RFC 7807](https://datatracker.ietf.org/doc/html/rfc7807) (and its successor RFC 9457) defines a standardized, machine-readable JSON structure for reporting HTTP errors:

```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "Resource with ID 'c1f7a0b5-74c6-43b5-9013-14a5e70dd7f8' was not found.",
  "instance": "/api/v1/resources/c1f7a0b5-74c6-43b5-9013-14a5e70dd7f8",
  "timestamp": "2026-10-19T11:38:00Z"
}
```

### Standard Fields:
* **`type` (URI):** Identifies the problem type (defaults to `"about:blank"` when no specific documentation URI is provided).
* **`title` (String):** Short human-readable summary of the problem (e.g. `"Not Found"`, `"Conflict"`).
* **`status` (Number):** The HTTP status code generated by the origin server.
* **`detail` (String):** Human-readable explanation specific to this occurrence of the problem.
* **`instance` (URI):** A URI reference that identifies the specific endpoint invocation.
* **`properties` (Object):** Optional custom key-value metadata (e.g. invalid parameter names, tracing correlation IDs, or custom timestamps).

## 2. Why Did ProblemDetail Work Without `spring.mvc.problemdetails.enabled`?

A common question:
> *"Why did my API return `ProblemDetail` JSON even without setting `spring.mvc.problemdetails.enabled: true` in `application.yml`?"*

### The Two Pathways for Errors in Spring Boot:

```mermaid
flowchart TD
    Error[Exception Thrown During Request] --> Match{"Is exception caught by custom @RestControllerAdvice?"}

    Match -->|Yes: Custom Exception (e.g. ResourceNotFoundException)| Handler["GlobalExceptionHandler.kt"]
    Handler --> Body["Hand-crafted ProblemDetail.forStatusAndDetail(...)"]
    Body --> Out1["Returns RFC 7807 ProblemDetail ✅\n(Works without ANY YAML setting!)"]

    Match -->|No: Unhandled Spring MVC Exception (e.g. 405 Method Not Allowed)| FrameworkCheck{"spring.mvc.problemdetails.enabled == true?"}
    FrameworkCheck -->|False (Default)| Legacy["Spring Boot DefaultErrorAttributes\n{'timestamp', 'status', 'error', 'path'} ❌"]
    FrameworkCheck -->|True| AutoRFC["ResponseEntityExceptionHandler automatically builds ProblemDetail ✅"]
```

1. **Custom Business Exceptions:** Handled by [`GlobalExceptionHandler.kt`](file:///src/main/kotlin/com/example/demo/infrastructure/adapter/in/rest/GlobalExceptionHandler.kt). Because our code explicitly instantiates and returns `ProblemDetail`, it **always** outputs RFC 7807 format regardless of YAML properties.
2. **Spring Framework Web Exceptions:** Built-in exceptions (`405 Method Not Allowed`, `415 Unsupported Media Type`, `MissingServletRequestParameterException`). These only produce RFC 7807 if `spring.mvc.problemdetails.enabled: true` is enabled; otherwise, Spring Boot falls back to the legacy `{"timestamp", "status", "error", "path"}` format for backwards compatibility.

## 3. Exposing ProblemDetail in Swagger UI / OpenAPI 3

By default, Swagger UI only shows HTTP 200/201 responses unless error responses are explicitly declared.

### Approach 1: Method-Level Annotations (`@ApiResponses`)
You can annotate individual controller methods with `@ApiResponse`:

```kotlin
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
@ApiResponses(
    value = [
        ApiResponse(responseCode = "201", description = "Resource created successfully"),
        ApiResponse(
            responseCode = "400",
            description = "Validation failure",
            content = [Content(mediaType = "application/problem+json", schema = Schema(implementation = ProblemDetail::class))]
        ),
        ApiResponse(
            responseCode = "404",
            description = "Resource not found",
            content = [Content(mediaType = "application/problem+json", schema = Schema(implementation = ProblemDetail::class))]
        )
    ]
)
fun create(@RequestBody request: CreateResourceRequest): ResourceResponse { ... }
```
* **Pros:** Highly granular per-method control.
* **Cons:** Violates DRY (Don't Repeat Yourself); requires dozens of repetitive annotations across every controller endpoint.

---

### Approach 2: Global Automated Customizer in `OpenApiConfig.kt` (Implemented in this Service)
Instead of repetitive annotations, we configure an **`OperationCustomizer`** and register `ProblemDetail` in the OpenAPI **`Components.schemas`** inside [`OpenApiConfig.kt`](file:///src/main/kotlin/com/example/demo/infrastructure/config/OpenApiConfig.kt):

```kotlin
@Configuration
class OpenApiConfig {

    @Bean
    fun customOpenAPI(): OpenAPI {
        val problemDetailSchema = Schema<Any>()
            .type("object")
            .description("RFC 7807 standardized Problem Detail error response")
            .addProperty("type", StringSchema().example("about:blank"))
            .addProperty("title", StringSchema().example("Not Found"))
            .addProperty("status", IntegerSchema().example(404))
            .addProperty("detail", StringSchema().example("Resource with ID was not found."))
            .addProperty("instance", StringSchema().example("/api/v1/resources/c1f7a0b5-74c6-43b5-9013-14a5e70dd7f8"))
            .addProperty("timestamp", StringSchema().example("2026-10-19T11:38:00Z"))

        return OpenAPI()
            .components(
                Components()
                    // Exposes reusable #/components/schemas/ProblemDetail in Swagger
                    .addSchemas("ProblemDetail", problemDetailSchema)
            )
    }

    @Bean
    fun globalProblemDetailResponses(): OperationCustomizer =
        OperationCustomizer { operation, _ ->
            val problemDetailRef = Schema<Any>().`$ref`("#/components/schemas/ProblemDetail")
            val problemContent = Content().addMediaType(
                "application/problem+json",
                MediaType().schema(problemDetailRef)
            )

            val responses = operation.responses
            // Automatically attaches 400, 401, 403, 404, 409, 422, and 500 error responses to EVERY endpoint in Swagger!
            if (!responses.containsKey("400")) {
                responses.addApiResponse("400", ApiResponse().description("Bad Request / Validation Error").content(problemContent))
            }
            if (!responses.containsKey("401")) {
                responses.addApiResponse("401", ApiResponse().description("Unauthorized - Missing, expired, or invalid OAuth2 Bearer token").content(problemContent))
            }
            if (!responses.containsKey("403")) {
                responses.addApiResponse("403", ApiResponse().description("Forbidden - Insufficient permissions or scopes").content(problemContent))
            }
            if (!responses.containsKey("404")) {
                responses.addApiResponse("404", ApiResponse().description("Resource Not Found").content(problemContent))
            }
            if (!responses.containsKey("409")) {
                responses.addApiResponse("409", ApiResponse().description("Conflict - Invalid resource state").content(problemContent))
            }
            if (!responses.containsKey("422")) {
                responses.addApiResponse("422", ApiResponse().description("Unprocessable Entity - Business rule violation").content(problemContent))
            }
            if (!responses.containsKey("500")) {
                responses.addApiResponse("500", ApiResponse().description("Internal Server Error").content(problemContent))
            }
            operation
        }
}
```

## 4. Anatomy of the Registered OpenAPI Schema

With this configuration:
1. **Under Schemas in Swagger UI:** A first-class `ProblemDetail` schema is rendered with sample values:
   ```json
   {
     "type": "about:blank",
     "title": "Not Found",
     "status": 404,
     "detail": "Resource with ID was not found.",
     "instance": "/api/v1/resources/c1f7a0b5-74c6-43b5-9013-14a5e70dd7f8",
     "timestamp": "2026-10-19T11:38:00Z"
   }
   ```
2. **Under Responses for Every Operation:** Swagger UI displays:
   * `200 OK` / `201 Created` with `ResourceResponse`.
   * `400 Bad Request` with `application/problem+json` -> `ProblemDetail`.
   * `401 Unauthorized` (Missing/expired Bearer token) with `application/problem+json` -> `ProblemDetail` ✅ *(No more "401 Undocumented"!)*.
   * `403 Forbidden` with `application/problem+json` -> `ProblemDetail`.
   * `404 Not Found` with `application/problem+json` -> `ProblemDetail`.
   * `409 Conflict` with `application/problem+json` -> `ProblemDetail`.
   * `422 Unprocessable Entity` with `application/problem+json` -> `ProblemDetail`.
   * `500 Internal Server Error` with `application/problem+json` -> `ProblemDetail`.

## 5. 60-Second Interview PREP Script

Use this script during technical interviews when asked: *"How do you document error responses in OpenAPI / Swagger?"*

> **Point:**  
> We use SpringDoc OpenAPI to globally register and expose our RFC 7807 `ProblemDetail` schema across all endpoints in Swagger UI.
>
> **Reason:**  
> By default, OpenAPI documentation only reveals success schemas (200/201). Frontend engineers need clear visibility into error contracts (400, 404, 500) so they can build robust client-side error handling without guessing fields.
>
> **Example:**  
> Instead of cluttering every controller method with repetitive `@ApiResponses` annotations, we defined a global `OperationCustomizer` in `OpenApiConfig.kt`. It registers a reusable `ProblemDetail` schema in `Components.schemas` and automatically attaches `400`, `404`, and `500` error responses with `application/problem+json` media types to every operation in the OpenAPI document.
>
> **Point (Restated):**  
> This ensures 100% contract synchronization between our `@RestControllerAdvice` error handler and our interactive Swagger documentation.
